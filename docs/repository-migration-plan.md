# 仓库搬迁与重命名备忘

## 背景

当前 2.0 分支已开始大幅改造产品形态和 UI，后续代码演进会逐步脱离 fork 前仓库的结构与定位。为了避免上游历史、包名、镜像名和自动化发布规则长期混杂，后续计划将项目搬迁到新的 GitHub 私有仓库，并完成仓库重命名。

本文只记录待办和风险点，不在当前阶段执行搬迁。

## 目标

- 新建 GitHub 私有仓库，作为后续主仓库。
- 仓库名称、镜像名称、应用标识统一收敛，避免继续暴露旧 fork 命名。
- 保留必要提交历史，便于追踪 2.0 改造过程；是否压缩历史后续再定。
- GitHub Actions 支持私有仓库下的 Docker 镜像构建与发布。
- 贡献者向 `main` 提交后仍可触发构建，但权限、令牌和发布范围必须明确。

## 待确认事项

- 新仓库 owner 与仓库名。
- 是否保留完整 Git 历史，还是以当前 2.0 基线初始化新仓库。
- GHCR 镜像命名，例如 `ghcr.io/<owner>/<repo>`。
- Docker 镜像是否继续发布 `latest`，还是只发布分支、提交 SHA、版本 tag。
- 贡献者提交 `main` 的权限模型：直接 push、PR 合并、还是受保护分支。
- 私有仓库下是否需要额外的 Docker/GHCR 令牌，或继续使用 `GITHUB_TOKEN`。

## 搬迁清单

1. 创建新的 GitHub 私有仓库。
2. 更新远端地址并推送目标分支。
3. 检查并替换 README、徽章、文档里的旧仓库链接。
4. 更新 `.github/workflows/docker.yml` 的镜像名称与触发分支。
5. 确认 `packages: write` 权限是否满足 GHCR 推送；不满足时配置专用令牌。
6. 检查部署脚本、Compose 文件、服务器拉取镜像地址。
7. 检查包名、应用名、浏览器标题、PWA 元数据和公开文案。
8. 配置分支保护、Actions 权限、Secrets 和 Environments。
9. 在空库和旧数据环境各跑一次构建、迁移、启动验证。
10. 旧仓库冻结或归档，并在 README 顶部标注新仓库位置。

## 构建与令牌注意事项

- 当前 Docker 工作流使用 `GITHUB_TOKEN` 登录 `ghcr.io`，并要求 `packages: write`。
- 私有仓库迁移后，优先验证 `GITHUB_TOKEN` 是否仍可推送目标 GHCR 包。
- 如果镜像包属于组织或需要跨仓库推送，应改用最小权限的 PAT 或 GitHub App token。
- 令牌只放在 GitHub Secrets，不写入仓库、Compose 文件或服务器脚本。
- 贡献者提交触发构建时，需要避免 fork PR 获取可写令牌；外部 PR 应只构建不推送。

## 回滚预案

- 搬迁前保留旧远端和旧镜像 tag。
- 新仓库 Actions 首次稳定前，生产部署继续使用旧镜像地址。
- 若迁移后 GHCR 权限异常，先切回旧镜像发布链路，再处理权限。
